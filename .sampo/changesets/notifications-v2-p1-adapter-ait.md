Serve notifications v2 on Apps in Toss. The host bridge answers the `notifications.v2.*` methods from a provider over `Notification.requestAgreement` (Toss 5.255.0 or later), configured with the new `notificationTopics` option (`templateSetCode` and `agreement` per topic; v1 `notificationTemplateCodes` become agreement-required topics), and the gateway exposes `notificationsV2` whenever the host offers the notifications event channel. Agreement answers map to `granted`, `already-granted`, and `denied`, a sheet without an answer within 120 seconds to `dismissed`, `TERMS_DISAGREED_MEMBER` to `action-required` (`host-settings`), and each decision carries `apps-in-toss.notification-agreement.v1` evidence for the backend's consent record. A launch whose referrer is `push` or `inbox` reaches the game once as a cold `opened` event with its landing route, and `presentation.getLaunchIntent()` answers `home` for it while a topic is configured. The v1 `notifications` methods are now served from the same provider and keep no session copy of an agreement, so `getStatus` reads `not-subscribed` for a topic that needs one even after the player agreed (`unsupported`, and `requestSubscription` `unavailable`, on Toss older than 5.255.0); read it through the notifications runtime instead. The `requestNotificationAgreement` host dependency is now typed as and defaults to `Notification.requestAgreement`, a new `readInitialUrl` dependency reads `Environment.initialURL` (the page URL serves where the host gives none), and `notificationAgreementTimeoutMs` may shorten the 120-second settle. Without any mapped topic the gateway still offers `notificationsV2`, whose capabilities read `configuration-required`.
