`@mpgd/game-services/notifications/client` adds `createGameServicesNotificationsClient`, the notifications runtime's backend over the game-services Worker's session routes (`/game-services/notifications`: consent, endpoints, reminders, notices) and its public `GET /providers`. It takes the commerce client's `baseUrl`, `fetch`, `headers`, and `getHeaders`, so a game gives both clients one header resolver, and the deployment `target` the Worker needs for a device registration. The game's identity supplies the current `{ playerId, sessionId }` and an authenticated subscription; no request carries a player or an installation, which the Worker reads from the session. Worker answers map to the codes the runtime acts on (`GameServicesNotificationsRequestError`, with the status, the Worker's error, and `Retry-After`): a 401 is a retryable `NOTIFICATIONS_TEMPORARILY_UNAVAILABLE`, a 404 or 405 on a session route `NOTIFICATIONS_CONFIGURATION_REQUIRED`, a 400 or 413 `NOTIFICATIONS_INVALID_INPUT`, and an answer outside the route's contract `NOTIFICATIONS_CONFIGURATION_REQUIRED`. Every conformance vector the service passes also passes with the runtime calling it through this client.

`resolveGameServicesRequestHeaders`, `GameServicesHeaderResolver`, and `GameServicesHeaderResolutionError` move to an internal module and are still exported from the package root and `./client`.
