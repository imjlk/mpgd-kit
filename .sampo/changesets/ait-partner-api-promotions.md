The Apps in Toss partner API client (`createAppsInTossPartnerApiClient` in `@mpgd/game-services/apps-in-toss-partner-api`) makes the three promotion (Toss points) calls over the same mTLS binding, so a game server no longer hand-rolls them: `issuePromotionKey({ recipient })` issues a payment key (`execute-promotion/get-key`), `executePromotion({ recipient, promotionCode, key, amount })` pays with it (`execute-promotion`), and `getPromotionExecutionResult({ recipient, promotionCode, key })` answers `SUCCESS`, `PENDING`, `FAILED`, or `NOT_FOUND`, the documented business error `4111` (`execution-result`). The recipient goes in one `x-toss-user-key` or `x-anon-key` header, as for functional messages. The calls keep the client's response-size limit, timeout, caller abort, and `AppsInTossPartnerApiError` with the partner API's `errorCode`; they refuse a bad amount, key, code, or recipient before sending anything, never retry, and do not follow redirects. The client only calls the partner API and grants nothing. Toss pays a key at most once and answers `4113` to a used key, so a retry with the same key cannot pay twice: store one key per grant before executing it, settle the grant from the execution result whatever an execute call answered, and issue a new key only after `FAILED` (the README's "One key per grant" has the full rules). A test fake that implements the whole `AppsInTossPartnerApiClient` interface needs the three new methods; one typed with `Pick<…>` does not.
